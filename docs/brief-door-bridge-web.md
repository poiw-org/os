# Brief: BLE unlock on the door, the bridge and the backend

You are adding phone unlocking over Bluetooth Low Energy to Doora, the door lock of the po/iw
hackerspace. A separate agent builds the phone app from `docs/brief-flutter-app.md`; it depends on
what you build, so your work comes first.

Read, before you change anything: `docs/ble-protocol.md` (normative; you implement it exactly),
`README.md`, `doora/README.md`, `web/README.md`, and the code named below. The door is live and
people rely on it to get in. Correctness and safety come before speed. Where this brief says "stop
and ask", do that instead of working around it.

## 1. What you deliver

1. **Door firmware** (`doora/`, ESP32 WROOM, no PSRAM): talks to the bridge over UART, issues
   challenges, verifies BLE requests, opens the door, journals.
2. **Bridge firmware** (new `bridge/`, ESP32-C3 Super Mini): a BLE peripheral that carries bytes
   between the phone and the door. No decisions, no secrets.
3. **Backend** (`web/supabase/`): the `ble-credential` edge function and a shared token signer.
4. **Web app** (`web/`): a small addition to the key page showing the bound phone.
5. **Test vectors** `docs/ble-test-vectors.json` (protocol section 7), generated by a script you
   commit, used by your tests and by the app agent's.

Out of scope: the phone app, remote unlock, key issuing, NFC behaviour, onboarding.

## 2. Why this shape

BLE could not run on the door itself. Measured on the live door: keeping the Bluetooth controller's
memory costs about 82 KB, leaving 61 KB free with the websocket up, below the 72 KB a TLS session
needs; starting NimBLE then panicked the door twice (`esp_reset_reason` 4). So the radio moves to a
separate ESP32-C3 and the door gains only a UART, a P-256 verifier and a small state machine:
a few KB of RAM, no heap in the hot path.

The trust model follows from that: the door is the authority, the bridge is untrusted plumbing
(protocol "Parts and trust"). Keep it that way. Nothing the bridge says is believed; the bridge
never sees a nonce before the door creates it.

## 3. State you inherit (uncommitted in the working tree)

- **Keep:** `doora/src/Net.*`, `Cloud.*`, `Realtime.*` and the `doora/README.md` note. When memory
  is too short for two TLS sessions, the REST task borrows the websocket's (`RealtimeEvents::yield`).
  It passed an OTA trial on the door. Review it and keep it.
- **Keep:** the `ENV` variable in `doora/makefile` (`make release ENV=<env>`).
- **Remove:** `doora/src/BleSpike.cpp`, the `BLE_SPIKE` blocks in `doora/src/Bt.cpp`, and
  `[env:ble_spike]` in `doora/platformio.ini`. They were a measurement.
- **Leave alone:** `doora/src/Pn532.*` and `doora/host_test/pn532_test.cpp` (the owner's work in
  progress), and the Bluetooth Classic console in `Bt.*`, which stays compiled out
  (`Bt::kEnabled = false`) and still releases the controller memory at boot.
- **Replace:** `docs/ble-unlock-brief.md` is superseded by this brief; delete it.

How keys work today, which you build on:

- A key is a row in `public.keys` and an RS256 JWT from `web/supabase/functions/keys/index.ts`
  (`signKey`, key pair derived from `RSA_KEY_SEED` in `_shared/rsa.ts`). The door verifies it in
  `doora/src/Jwt.cpp` and decides in `doora/src/Access.cpp`; disabled keys arrive as a blacklist of
  `jti`s (`BlacklistSet`, synced by `Cloud.cpp`, pushed by `Realtime.cpp`).
- A virtual key has `serial_number is null` and today gets `aud: "virtual"`, which the door rejects
  by design (`parseUid` fails).
- `web/supabase/migrations/20261104030000_virtual_key_device.sql` already adds `device_pubkey`,
  `device_name`, `device_bound_at`, a unique index, an immutable-binding trigger and
  `can_use_app()` / `can_use_app_as(uuid)`. It refers to a `ble-credential` function that does not
  exist yet. Read that migration's comments; they are part of the design.

## 4. Hardware

| Signal | Door (ESP32) | Bridge (C3 Super Mini) |
| --- | --- | --- |
| Door TX → bridge RX | GPIO 17 (`BRIDGE_TX`) | GPIO 20 (UART RX) |
| Bridge TX → door RX | GPIO 16 (`BRIDGE_RX`) | GPIO 21 (UART TX) |
| Ground | GND | GND |
| Power | 5V / VIN | 5V |
| Optional reset | `BRIDGE_RESET` (e.g. GPIO 27) | the board's EN/RST pad, if it is reachable |

- GPIO 16/17 are free in the current pin map (`doora/src/Pins.h`, `config.example.h`) and on a
  WROOM module. Add `BRIDGE_RX`, `BRIDGE_TX` and an optional `BRIDGE_RESET` to `Pins.h` with
  defaults, and document them in `config.example.h`. Do not use strapping pins.
- Verify the C3 board's pinout before relying on it: Super Mini clones differ. Its console is the
  native USB serial, so UART0 on GPIO 20/21 is free for the link; confirm that in its schematic.
- Many Super Mini boards have a weak antenna. Mount it clear of metal and measure RSSI where the
  user will stand; the app's proximity threshold depends on it.
- If `BRIDGE_RESET` is wired, the door pulses it (open-drain, 100 ms low) when the bridge has been
  silent for 30 s, at most once a minute.

## 5. Protocol

Implement `docs/ble-protocol.md` exactly. If you find a flaw in it, stop and ask; do not diverge
silently. Generate `docs/ble-test-vectors.json` with a committed script
(`docs/tools/ble_vectors.py` or `.ts`) using a well-known crypto library, and make the door's host

## 6. Door firmware

Follow the existing style: small portable modules with host tests in `doora/host_test`, I/O at the
edges, fixed buffers, no heap in the tap path, comments that say why.

- **`BridgeLink.*`** (portable): COBS encode/decode, CRC, frame types from protocol section 6, a
  streaming decoder fed byte by byte with a fixed 1.2 KB buffer. This is the only implementation of
  the link; the bridge firmware compiles the same files (section 7).
- **`BleProto.*`** (portable): challenge and result encoding, request parsing, the signed-message
  builder. No UART or BLE types.
- **`P256.*`**: vendor micro-ecc (kmackay, BSD-2-Clause) in `doora/vendor/micro-ecc/` with its
  licence, built for secp256r1 with only what verification needs. Wrap it as
  `p256Verify(const uint8_t pub[65], const uint8_t hash[32], const uint8_t sig[64])`, and validate
  the point. Portable and allocation-free like `Rsa.cpp` and `Sha256.cpp`. Test with Wycheproof
  ECDSA P-256 vectors, including invalid points, `r` or `s` of zero or ≥ n, and high-`s`
  signatures. Measure one verification on the device and record it in the README.
- **`Jwt.*`**: add `cnf[65]`, `hasCnf` and an audience kind (tag serial or BLE) to `KeyClaims`.
  Make `"ble"` a recognised `aud` without loosening the tag path. Mind the fixed buffers
  (`payload[576]`, the 16-byte pattern in `findValue`, `readString` capacities).
- **`Access.*`**: a BLE decision that shares the blacklist and date rules with `decide()` instead of
  copying them, and keeps the serial check for tags only.
- **`Bridge.*`** (I/O): owns `Serial2` (RX buffer 2 KB), pings, tracks the bridge's version and
  liveness, holds the current connection number and its nonce, and hands one completed request to
  `loop()` through a single slot, the way `Reader` hands over a tag (`take()` / `release()`).
  Serviced from `loop()`; it never blocks.
- **`main.cpp`**: a `handleBle()` next to `handleTag()`, reusing its logging, journaling,
  `Actuators` calls and the clock and blacklist it already uses. Verification runs on the loop
  task, as tag verification does. Answer every request with a `RESULT`.
- **Journal**: `JournalRecord` is a fixed 64-byte on-flash format; do not change its size. Add a
  `JournalFlags` bit (16) for BLE, leave `uid` empty, and have `journalToJson` add
  `"source":"ble"` to `metadata`. Rate-limit denials like failed taps. Check that every `reason`
  the door can send is allowed by the `entries.reason` constraint (init migration); add values in
  a new migration if needed.
- **`status`**: a `bridge` line: online or not, its firmware and link versions, BLE opens and
  denials, frames dropped.
- **Memory**: after the change, idle free heap stays within 4 KB of today's 144 KB. Prove it with
  `status` on a bench board.
- **Tests**: every invariant in protocol section 5, the test vectors, COBS and CRC edge cases
  (empty frames, frames of all zeros, truncated frames, garbage between frames), reassembly
  limits, a request for a stale connection number, the nonce lifecycle, the 2 s hold after a
  failure, and the decision table. `make -C doora test` passes with its `-Werror` and sanitizers.
- **Docs**: update `doora/README.md`: modules, the decision diagram, wiring, failure table (bridge
  unplugged, bridge flooding the link, power cut mid-unlock), known limits.

## 7. Bridge firmware (`bridge/`)

- PlatformIO, board `esp32-c3-devkitm-1` or a better-matching definition, Arduino framework, and
  NimBLE-Arduino. Check the current NimBLE-Arduino version and its API on the registry before you
  write code: 2.x changed the callback signatures from 1.x. Pin the version.
- Compile `doora/src/BridgeLink.*` and `doora/src/Crc.h` from their place in the repository (for
  example `build_flags = -I../doora/src` and a `build_src_filter` entry). Do not copy them.
- Behaviour, all from protocol sections 2 and 6: advertise only while the door pings; one
  connection; on subscribe send `CONNECTED`; forward the door's `CHALLENGE` and `RESULT` as
  notifications; reassemble writes into one `REQUEST`; enforce the reassembly limits; disconnect on
  the 10 s timeout and after a `RESULT`; send `GONE` on every disconnect.
- Request an ATT MTU of 247 and support whatever the phone negotiates down to 23.
- A task watchdog that restarts the bridge if its loop stalls. Log to the USB console only.
- No OTA. The bridge is flashed over USB; it is deliberately dumb so it rarely changes. Put its
  version in `HELLO` and document the flashing steps in `bridge/README.md`, including the wiring
  table.
- Test the bridge's reassembly and timeout logic on the host where it is portable.

## 8. Backend (`web/supabase/`)

- **Shared signer.** Move `signKey` from `functions/keys/index.ts` to `functions/_shared/` so every
  token is built in one place. For a virtual key with a bound device it signs `aud: "ble"` and
  `cnf`; otherwise the claims are unchanged. `renew` in `keys` must keep the binding and store the
  new token in `keys.jwt`. Assert the token length against 860 characters.
- **`functions/ble-credential/index.ts`**, in the style of the existing functions (`handlePost`,
  `serviceClient`, `accessToken`, `callerId`; `verify_jwt` off at the gateway, the function
  authorises the caller itself):

  `POST { key_id, device_pubkey, device_name }` → `{ jwt, not_before, expires_at }`

  - The caller owns the key; the key is virtual, not disabled; the user is not blocked;
    `can_use_app_as(caller)` is true. Otherwise 403 or 404 with a sentence a member understands.
  - `device_pubkey` is 87 base64url characters decoding to 65 bytes; import it with WebCrypto as a
    P-256 public key before storing it, so a point off the curve is refused.
  - `device_name` is 1 to 64 characters after trimming.
  - No device yet: bind it. Same device: return the current credential (this is how the app picks
    up a renewal). Another device: 409, "This key is set up on another phone". Map a unique
    violation (`23505`) to the same 409.
  - Re-sign on bind; on a same-device call return the stored token if its claims match the row,
    else re-sign.
- **Grants.** Confirm which roles can read `keys.jwt` and the device columns (the grants in the
  init migration and the note in the device migration). The app must get its credential from this
  function. If a member can read `keys.jwt` directly today, decide with the owner whether to
  revoke it; stop and ask.
- **Migrations** only if needed, expand-only, each with a rollback note in its header like the
  existing ones.
- Test against a local stack (`supabase start`), never production: binding, idempotence, the 409,
  a disabled key, a blocked user, a malformed and an off-curve public key, renewal keeping `cnf`.

## 9. Web app (`web/`)

- On the key page (`src/routes/os/keys/[id]`), for a virtual key: the bound phone's name and when
  it was bound, or "Not set up on a phone yet". Admins and the key's owner see it.
- In the activity feed, entries with `metadata.source = "ble"` read as opened "with a phone".
- Follow `web/design.md` and the existing components; regenerate `src/lib/database.types.ts` if the
  schema changes; `pnpm lint` and `pnpm check` pass.

## 10. Order and done

1. Test vectors and the portable modules with host tests.
2. Backend signer and `ble-credential`, tested locally.
3. Door and bridge on a bench (a spare ESP32 and the C3), first with a throwaway test client
   (`docs/tools/ble_client.py` with `bleak`), which also serves the app agent.
4. A 24-hour bench soak: Wi-Fi drops, uploads, token renewals, repeated unlocks, the bridge
   unplugged and replugged, and the door rebooted mid-unlock.
5. Ask the owner before anything reaches production (section 11).

Done means: every invariant has a passing test; `make -C doora test`, the bridge build, the web
checks and the function tests pass; the test client unlocks the bench door with both Wi-Fi and
internet off; a disabled key is refused after the door's next sync; the memory figure in section 6
holds over the soak; the READMEs are updated.

## 11. Rules

- Ask before: releasing firmware to the door (`make release`), applying migrations or deploying
  functions to the production Supabase project, revoking a grant, adding a dependency not named
  here.
- Never commit secrets, `config.h`, seeds or tokens. Never put a real user's data in tests or
  vectors.
- Commit in small steps in the repository's style (`git log`). Do not push or open a PR unless
  asked.
- Report plainly: failing tests with their output, anything skipped, anything measured only on the
  bench.
